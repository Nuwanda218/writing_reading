# 大模型应用：让 LLM 听你使唤的那张嘴

> 变更日志：
> - v1.0 | 2026-08-18 15:04:30 | 初版

你已经发出过调用大模型的请求了——你见过 `model`、`messages`、`response` 这些字段，见过 `Authorization`、`x-api-key` 这些请求头，也可能在几个厂商的文档之间来回切换过，被五花八门的格式弄得有点晕。

这篇文章，就是给这团迷雾开灯的。它回答三个问题：**一次 LLM 调用到底是什么？各大厂商的协议长什么样、什么时候用哪个最好？** 看完你会明白：这些协议看起来千奇百怪，本质上都是同一句话的方言——"给这个模型一段话，让它接着说下去"。

## 一、它是什么：一次调用，就是一个 HTTP 请求

先拆掉一层神秘感：**所谓"调用大模型"，在技术上就是一次普通的 HTTP 请求。** 和你用浏览器打开网页、用手机刷 App，走的是同一条路。

完整链路是这样的：你的程序拼好一段 JSON → 通过 HTTP POST 发给厂商的服务器地址（URL）→ 厂商的网关做身份验证、计费 → 把请求转给 GPU 集群上正在跑的模型 → 模型算出回复 → 一段 JSON 流回你的程序。

所以一次调用，由三块拼成，这也是**所有厂商**共同的骨架：

1. **URL**——去哪家、哪个接口。比如 `https://api.openai.com/v1/chat/completions`。各家的区别，一半都藏在这串地址里。
2. **请求头（Headers）**——你是谁、用什么格式交流。认证书信、协议版本，都在这里。
3. **请求体（Body）**——你说了什么、想让模型怎么回答。你见过的 `chat`、`model`、`response` 那些字段，全住在这里。

但在这之前，有一个更底层的事实要先钉进脑子里——**LLM 接口的本性，是一个"接话茬"机器。**

请你忘掉"对话框"这个直觉，因为它会误导你。你发给模型的不是一个"问题盒子"，而是一串文本；模型做的，是**接着这串文本往下写**。你在界面上看到的"多轮对话"，并不是模型记得你俩聊过什么——而是调用方（你的程序）把**从第一句到现在的每一句话，原封不动地打包重发**给模型，模型再接着最后一句话续写。

这就是那句名言的出处："模型没有记忆，所谓记忆，是每次都把聊天记录背一遍。" 这个事实会贯穿全文，后面你会看到它如何决定了"上下文越长越贵"、如何决定了各家协议的形态。

## 二、请求体：那些你看过的字段，都是干什么的

现在我们把一个典型请求体的字段摊开，用自然语言逐个过一遍。别怕——你见过的大多数字段，全世界协议都共用，只是名字略有出入。

**`model`：选哪台发动机。** 指定用哪个模型（"gpt-4o""claude-sonnet-4-6""deepseek-chat"）。每家都有自己的型号清单，传错名字直接报错。

**`messages`：你要喂的整段对话。** 这是一个数组，装着一行一行的"话"。每一行由 `role`（说话的人）和 `content`（说的内容）组成。`role` 只有三种：

- `system`——**导演**。告诉模型"你是谁、按什么规矩办事"（"你是一个严谨的中文老师，回答不超过 50 字"）。注意：**在 OpenAI 系里，system 是 messages 里的一个角色；而在 Anthropic 的协议里，system 被单独拎出来成了顶层参数**——这是两派最大的格式分歧之一，第四节细讲。
- `user`——**你**。每次用户输入都变成一行。
- `assistant`——**模型**。每次模型的回复，也要原样塞回 messages 里，否则模型不知道"自己刚才说过什么"。

**`temperature`：随机性旋钮。** 0 到 2 之间的数。调低→回答稳定、机械、字面直译；调高→天马行空、爱发散。写代码调到低，写诗调到高。

**`max_tokens`（或 `max_output_tokens`）：回答多长。** 限制模型最多输出多少字。别设太小——模型话说到一半被截断是新手最常见的困惑之一。

**`stream`：流式开关。** `false`（默认）时，模型憋完整段话再一次性吐给你，短则几秒、长则半分钟，期间你看着转圈；`true` 时，模型算出一个字吐一个字，你看到的就是 ChatGPT 那种逐字蹦出的效果。想做"打字机"体验就开它。

**`tools`：工具箱清单。** 告诉模型"你手上有这些工具可用"。模型不会真的去执行——它只是会在回答里说"我建议调用 XX 函数，参数是 YY"，真正的执行由你的程序完成。这是 Agent 的地基，第五节展开。

**`response_format`：输出格式约束。** 强制模型按 JSON 或其他格式输出，专治"让它给个 JSON 它偏要加句寒暄"的毛病。

**把这六个字段装进同一个画面**：你手里有一台"接话茬机器"，`model` 选机器，`messages` 递话，`system` 立规矩，`temperature` 调脾气，`max_tokens` 限话量，`stream` 定语速。所有协议的字段，都是这一幅画的变体。

## 三、请求头：每家的"家门钥匙"

请求体是"你说了什么"，请求头是"你是谁、我们按哪套规矩聊"。各家最大的差异之一，就藏在请求头里。

**`Content-Type: application/json`——几乎全世界的接口都要求这一条**，声明"我发的是 JSON"。没有它，服务器连你的请求都不会读。

**`Authorization: Bearer <key>`——最通用的认证书信。** OpenAI、DeepSeek、通义、智谱、Gemini、Ollama，全都认这一条。你只要把 `Authorization: Bearer` 加上你的 API Key 塞进请求头，身份就通过了。这也是"OpenAI 兼容"协议的一个重要标志——**凡是收这个头的，基本都能用 OpenAI 的代码改个地址就跑通。**

**Anthropic 的特殊之处：不用 Bearer，用 `x-api-key`，还多一个 `anthropic-version`。** Claude 的 API 认两把钥匙：`x-api-key: <你的密钥>`（身份），以及 `anthropic-version: 2023-06-01`（协议版本号——声明"我按 2023 年 6 月的协议格式跟你说话"）。**这两条头，是 Anthropic 与"OpenAI 兼容"阵营最扎眼的分界线。** 你换用 Claude 时如果报"缺失 headers"，十有八九是忘了这两条。

为什么这么不统一？两个历史原因：一是各厂 API 是不同时期独立设计的，没等"统一标准"出来，各自的生态就长起来了；二是认证方式的差异某种程度上也是"锁客"手段——换了家，至少得改两行代码。

## 四、各家协议全景：长什么样，什么时候用最好

现在把主要玩家的协议摊开，每家讲三件事：**长什么样、标准差在哪、什么时候用最好。**

### OpenAI 系：事实标准

**Chat Completions 协议**——全球 LLM 接口的"普通话"。OpenAI 2019 年起定下的这套格式（POST 到 `/chat/completions`，发 `messages` 数组），后来被 DeepSeek、通义、智谱、OpenRouter、Ollama 等**几乎所有玩家照抄**——它们对外宣称"OpenAI 兼容"，意思是"你用 OpenAI 的代码，改个 base_url（服务器地址）就能调我"。你看到的各种"chat"字样，源头就是这套协议。

**什么时候用最好**：绝大多数情况。它生态最全（任何语言的 SDK 都支持）、资料最多、兼容性最强。**你拿不准该用哪家协议时，选 OpenAI 兼容的准没错。**

### OpenAI Responses API：新一代

2024 年推出的新接口（`/responses`），口号是"给 Agent 时代准备的"：把工具调用、记忆、搜索这些高频能力直接内建成字段，而不是靠你手动拼 `tools`。它解决的是 Chat Completions 的痛点——随着模型从"聊天"走向"干活"，那些能力分散在不同字段里，调用方要自己拼半天。

**什么时候用最好**：当你要构建 Agent（让模型用工具、带记忆、持续完成任务）时。但注意：**生态成熟度还赶不上 Chat Completions**，很多第三方工具仍只兼容老协议。

### Anthropic Messages：System 独立派

Claude 家的协议（POST 到 `/v1/messages`）。两个标志性差异：**一是认证用 `x-api-key` + `anthropic-version`（不是 Bearer）；二是 `system` 不放进 messages 数组，而是单独作为顶层参数**——在 Anthropic 看来，"导演"和"演员"不该混在一个名单里。

**什么时候用最好**：当你深度使用 Claude 的特性时——长上下文（Claude 的强项）、精细的 system 提示工程、以及 Anthropic 生态特有的能力（如函数调用、视觉理解都做得更顺）。如果只是顺手调一下，走 OpenAI 兼容的第三方也行。

### Google Gemini：多模态与超长上下文

接口叫 `generateContent`（生成内容），认证可以走 API key 或 OAuth。它和"OpenAI 兼容"阵营不互通——**SDK、字段名、调用方式都是另一套方言**。

**什么时候用最好**：输入里混着图片、视频、音频（Gemini 的原生多模态是强项），或者你需要超长上下文（Gemini 的百万级 token 窗口，能一次读完整本书）。纯文本聊天场景，它的协议独特性反而是负担。

### 国产三剑客：DeepSeek / 通义 / 智谱

三家全部走 OpenAI 兼容：DeepSeek 的 `https://api.deepseek.com/v1`、通义千问的 `dashscope`、智谱 GLM 的 `open.bigmodel.cn`。**你不需要为它们学新协议**——OpenAI 代码改个地址就能调。

**什么时候用最好**：要国内部署、数据合规（不出境）；要中文场景优化；以及——**DeepSeek 是当前性价比之王**，token 价格远低于国际大厂，适合量大、对价格敏感的场景。

### Ollama：本地模型

`localhost` 上的小模型运行器。兼容 OpenAI 的 `/v1/chat/completions`，也有自己的原生接口。模型跑在你自己的电脑上。

**什么时候用最好**：数据不出本机（隐私/合规）、完全离线、开发调试想白嫖不花钱、或者电脑跑得动的小模型够用时。代价是模型能力和云端大厂差距明显。

### OpenRouter：一个 Key 调所有

聚合平台。你注册它、充钱、拿一个 key，然后用 OpenAI 兼容的格式调几百家模型——`model` 字段填 `anthropic/claude-sonnet-4`、`openai/gpt-4o`、`deepseek/deepseek-chat`，想换就换。

**什么时候用最好**：要同时对比多家模型的效果、要防止被某一家锁死、或者不想给各家分别充值管理。它本质是"模型界的路由器"。

## 五、横切公共能力：每家都有，只是字段名不同

四件事，所有协议都支持，只是命名和放置位置不同。它们决定了"能不能做出真正可用的产品"。

**流式输出（Streaming / SSE）**：让回复逐字蹦出来。底层技术叫 SSE（Server-Sent Events）——服务器在一条连接上持续往你这里推文本，推完一个"字"你就画一个"字"。用户为什么非开不可？因为大模型回答前有个"思考前摇"，一次性返回会让用户干等好几秒，而流式让用户"感觉它活着"。几乎所有聊天产品都用流式。

**工具调用（Function Calling / Tools）**：这是 Agent 的地基，值得讲透。它解决一个关键难题：**LLM 只会"说"，不会"做"。** 你问它"帮我查下北京的天气"，它其实查不了——它不知道天气接口在哪，也没有真的去调用任何东西。工具调用的流程是：你把工具清单（名字、参数格式、用途说明）放进 `tools` 字段 → 模型决定"这题需要查天气"，于是回复一个特殊结构："我建议调用 `get_weather`，参数 `city=北京`" → **你的程序收到这个指令，自己去调用真实的天气 API** → 把查到的结果作为新的一行 `tool` 角色消息回喂给模型 → 模型基于真实数据组织最终回答。看清楚分工：**模型负责"决定调什么"，你的程序负责"真的去调"。** 二者缺一不可。

**结构化输出（Structured Outputs）**：强制模型返回完全合法的 JSON（用 `response_format` 或 Anthropic 的 `output_format`）。防止它给你"我查了一下……{"city":"北京"}……"这种夹带寒暄的脏 JSON。做任何"模型输出要进程序"的场景（接数据库、喂给前端、驱动决策）都必须用它。

**多轮对话与缓存（Prompt Caching）**：还记得第一节那句"模型没有记忆，每次都要重发全部历史"吗？它带来一个现实问题：**对话越长，每次重发的 token 越多，越贵、越慢。** 各家因此都推出了"提示缓存"：如果连续几次请求的文本开头一模一样（也就是历史没变），服务器就复用上次算好的中间结果，只对新加的部分重新计算——**价格和速度都大幅优化**。Claude 和 OpenAI 都默认支持，调用方无需改代码，只是账单变友好。这也是"上下文越长越贵"这个定律唯一被松动的口子。

## 六、怎么选：一张决策图

把第四节和第五节的"什么时候用最好"收拢成一张决策图，你可以照着走：

```
要不要数据不出本机？ ──是──→ Ollama（本地模型）
        │否
要不要对比/切换多家模型？ ──是──→ OpenRouter（一个 key 全搞定）
        │否
要不要国内合规 / 极致低价？ ──是──→ DeepSeek / 通义 / 智谱（全 OpenAI 兼容）
        │否
要构建 Agent / 深度用工具？ ──是──→ OpenAI Responses API
        │否
要不要多模态 / 超长上下文？ ──是──→ Gemini
        │否
深度用 Claude 特性？ ──是──→ Anthropic Messages
        │否
──────────────→ OpenAI Chat Completions（默认答案）
```

（这条图的顺序是有讲究的：**越往下，越是"没有特殊需求时的通用选择"**。绝大多数项目走到最后，落点就是 OpenAI 兼容协议——这也是它成为事实标准的原因。）

再补五条放之四海皆准的实操建议：

1. **永远先开流式**——延迟是用户体验的命脉，除非你的下游只能吃完整 JSON。
2. **该重试就重试**——模型服务偶尔抖动，加"失败后等 1 秒、2 秒、4 秒重试"的退避策略，能救回大量偶发错误。
3. **Key 是钱**——API Key 要放环境变量/密钥库，绝不硬编码进代码、更不提交进 Git；按用途分多个 Key 以便追溯和限额。
4. **设超时**——网络不可靠，给请求设一个合理超时（如 60 秒），宁可失败重试，也不要无限挂起。
5. **预热成本意识**——`temperature` 默认值各厂商不同（OpenAI 默认 1，Anthropic 默认 1）；`max_tokens` 别设太小被截断；长历史对话记得用缓存或主动压缩。

**总结判断**：大模型调用这门学问，剥到底就两层——**一是认清"LLM 接口是一台接话茬机器"（无状态、全量重发），二是认准"OpenAI 兼容是事实标准，特殊需求再往两边看"（本地→Ollama，切换→OpenRouter，Agent→Responses，Claude 特性→Anthropic，国内→国产，多模态→Gemini）。** 你之前看到的那一团字段和请求头，从此会变成一副你认识的骨架：选发动机、递话、立规矩、调脾气、限话量、定语速——然后给模型配上工具和输出约束，让它从"会说"变成"会干活"。

下一片叶子，你可以爬：**工具调用的完整回合**（从你提问到模型拿到真实数据，逐步拆解一次真实调用）、**流式传输是怎么实现的**（SSE 和 token 流的底层）、**结构化输出的 schema 怎么设计**（怎么让模型吐的程序能直接用）。你挑，我们继续。
