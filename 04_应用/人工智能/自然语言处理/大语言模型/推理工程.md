# 推理工程：让大模型"吐得快一点、便宜一点"

> 变更日志：
> - v1.0 | 2026-08-22 10:39:56 | 初版：O(n²) 注意力、KV 缓存、上下文窗口、推理成本

训练一个大模型很贵（《GPT 的诞生》讲过，上百万美元一次）。但你可能没意识到：**让一个训练好的模型回答你的问题，也很贵。** 推理（Inference，模型生成回答的过程）每天都在发生，它慢不慢、贵不贵，直接决定你能不能大规模用它。这篇讲推理工程——怎么让大模型"吐得更快、更便宜"。

## 一、先看清：推理到底贵在哪

回顾《大语言模型》"一次调用"那节：每生成一个词，模型都要**从头跑一遍整个流程**——对整句做注意力计算。有两个地方特别贵：

**贵点一：注意力是二次方复杂度（O(n²)）。** 这是《Transformer》收尾埋的伏笔。一句话有 n 个 token，每个 token 要和所有 n 个 token 算"配对"（Q 问 K），所以一共要算 **n × n** 次。token 数翻一倍，计算量翻四倍。**句子越长，注意力计算爆炸式变贵。**

**贵点二：生成是逐 token 循环。** 一个回答几百个词，就要重跑几百次"整句注意力"。上下文越长、回答越长，跑的次数越多、每次越贵。

两个叠加，就是"长对话 + 长回答"= 又慢又贵的全部原因。推理工程所有的招，都是在对付这两个贵点。

## 二、KV 缓存：别重复算已经算过的

第一个、也是最经典的优化，叫 **KV 缓存（KV Cache）**。

原理一句话：**你已经算过的中间结果，别重算，存起来下次直接用。** 回顾注意力计算：每个 token 在算注意力时要先生成 K（键）和 V（值）。你生成第 5 个词时，要重新算"第 1~4 个词"的注意力——但等等，**第 1~4 个词的 K 和 V，你在生成第 4 个词时已经算过了**，它们又不会变。

所以 KV 缓存的招数：**把已经算过的每个词的 K 和 V 存进内存，下次生成新词时，只算"新词自己的 K 和 V"，老词的直接取出来用。** 生成第 100 个词时，99 个老词的 KV 都是白拿的——省掉的计算量随生成长度线性增长，句子越长省得越多。

用《大语言模型》那节的比喻：以前每吐一个词就"整句从头读一遍"，KV 缓存让模型变成"读到哪儿记到哪儿，下次接着读"——**从每次全量重算，变成增量续算。** 这是今天所有大模型 API 都在用的基础设施，也是它们能"实时出字"的关键。代价是**吃内存**：缓存 10 万 token 的 KV 很占显存，这又引出了上下文窗口的瓶颈。

## 三、上下文窗口：为什么模型"记不住"太长

**上下文窗口（Context Window）**，就是模型一次能"看到"的 token 上限（比如 8K、32K、128K、1M）。超过窗口的输入，模型直接看不见。为什么有限制？两个原因，正好对应两个贵点：

1. **注意力 O(n²)**：窗口翻倍，计算量翻四倍——窗口大到某个点，算不动。
2. **KV 缓存吃内存**：缓存量和 token 数成正比，窗口越大，要存的 KV 越多，显存装不下。

所以"长上下文"一直是各家的军备竞赛：**模型要能看更多，就必须同时解决"算得快"和"存得下"。** 现在的解法有：**稀疏注意力**（不是每个 token 都看所有 token，只看附近的 + 跳着看远的，把 O(n²) 砍下来）、**滑动窗口**（只看最近的一千个词，更远的用摘要替代）、**高效 KV 缓存压缩**（量化、淘汰不重要 token）。这些技术，本质上都是在"尽量多看"和"算得动存得下"之间找平衡。

对使用者的实用含义：**超长文档别指望模型全记住**——要么用 RAG（检索增强生成，只把相关的几段喂进去），要么让它分段处理。硬塞超长上下文，只会又慢又贵还记不住。

## 四、推理成本：按 token 算钱

你调 API 时，账单是按 **token** 算的（《大模型应用》讲过）。两个数相乘：**单价 × token 数量**。token 数量又分两部分——输入（你发的，含全部历史）+ 输出（模型吐的）。所以：

**成本 =（输入 token 数 + 输出 token 数）× 单价**

这带来几个实用的省钱结论：

- **历史越短越便宜**：每次对话都重发全部历史（回收"模型没记忆"），所以聊天记录越长，输入 token 越多，越贵。**精简历史、主动摘要旧对话**，是省钱第一招。
- **输出比输入贵**（通常单价更高）：让模型"少说废话"（限制 max_tokens、要求简短）能省一大笔。
- **prompt 缓存（Prompt Caching）**：同一段开头（比如系统提示）连续请求时，服务商缓存中间结果，便宜很多——这正是《大模型应用》第六节提过的"提示缓存"，现在你知道它内部是什么了：本质上是 KV 缓存的商业化运用。

## 五、其他提速手段：点到为止

几个常用的工程招数，你知道存在即可：

- **量化（Quantization）**：把模型的数字从"高精度"压成"低精度"（比如把 32 位浮点数压成 8 位整数），模型体积小好几倍、算得快、吃显存少——代价是精度略降。这是让大模型跑在普通电脑上的关键。
- **批处理（Batching）**：多个用户的请求拼在一起同时算，GPU 的并行能力充分利用，摊薄成本——这是 API 服务商降价的底层手段。
- **投机采样（Speculative Decoding）**：用一个"小模型"先猜一串词，大模型只负责"批改"——猜对了直接通过，省掉大模型逐词重跑。

**总结判断**：推理工程的全部智慧，就一句话——**把"每生成一个词就全量重算"这个笨办法，优化成"能复用就复用、能少算就少算"。** KV 缓存复用中间结果，稀疏注意力砍掉无谓计算，量化压缩体积，批处理摊薄成本。你日常感受到的"大模型还挺快"，背后是这么一堆工程细节在兜底。
