训练一个大模型很贵（《GPT 的诞生》讲过，上百万美元一次）。但你可能没意识到：**让一个训练好的模型回答你的问题，也很贵。** 推理（Inference，模型生成回答的过程）每天都在发生，它慢不慢、贵不贵，直接决定你能不能大规模用它。这篇讲推理工程——怎么让大模型"吐得更快、更便宜"。

## 一、先看清：推理到底贵在哪

回顾《大语言模型》"一次调用"那节：每生成一个词，模型都要**从头跑一遍整个流程**——对整句做注意力计算。有两个地方特别贵：

**贵点一：注意力是二次方复杂度（O(n²)）。** 这是《Transformer》收尾埋的伏笔。算一笔具体的账：一句话有 n 个 token，每个 token 的 Q 都要去和所有 n 个 token 的 K 做点积（每对是 d 维向量，要做 d 次乘加），所以注意力总共要算 **n × n × d** 次运算。n 是 1000 时，就是 1000×1000×d——**n 翻一倍，计算量翻四倍。** 句子越长，注意力计算爆炸式变贵。

**贵点二：生成是逐 token 循环，而且分两段。** 一次完整的推理，其实分成两个计算性质完全不同的阶段：

- **预填充（Prefill）**：你发来一整段输入（比如 1000 个 token），模型一次性把整段处理完——这段算得快，因为可以并行、算力吃满。它算的是"第一个输出 token"。
- **解码（Decode）**：从第一个输出 token 开始，每生成一个 token，都要对"全部上下文 + 已生成的"再跑一遍——**而且是一个 token 一个 token 来，没法并行，主要卡在内存读取上。** 回答 300 个字，就是 300 次串行的解码步。

所以"长对话 + 长回答"慢，主要在解码段：**每吐一个词，整段重跑一次，而且不能并行。** 推理工程所有的招，几乎都是在对付解码段的这两个问题——算得重、不能并行。

## 二、KV 缓存：别重复算已经算过的

第一个、也是最经典的优化，叫 **KV 缓存（KV Cache）**。

原理一句话：**你已经算过的中间结果，别重算，存起来下次直接用。** 回顾注意力计算：每个 token 在算注意力时要先生成 K（键）和 V（值）。你生成第 5 个词时，要重新算"第 1~4 个词"的注意力——但等等，**第 1~4 个词的 K 和 V，你在生成第 4 个词时已经算过了**，它们又不会变。

所以 KV 缓存的招数：**把已经算过的每个词的 K 和 V 存进内存，下次生成新词时，只算"新词自己的 K 和 V"，老词的直接取出来用。**

**具体省多少？算一笔账。** 生成第 100 个词时，没有 KV 缓存，要重新算一遍"第 1~100 个词"的整个前向（100 个词的全量注意力）；有 KV 缓存，只需要算"第 100 个词自己"的前向（1 个词的注意力），99 个老词的 K/V 直接取用。**省掉约 99/100 的计算——而且越往后省得越多，到第 1000 个词省掉 999/1000。** 这就是"为什么带 KV 缓存能实时出字"的量化答案。

用《大语言模型》那节的比喻：以前每吐一个词就"整句从头读一遍"，KV 缓存让模型变成"读到哪儿记到哪儿，下次接着读"——**从每次全量重算，变成增量续算。** 这是今天所有大模型 API 都在用的基础设施。

**代价是吃内存，而且这笔账很吓人。** KV 缓存占多少，粗略公式：**缓存大小 ≈ token 数 × 层数 × 注意力头数 × 每头维度 × 2（K 和 V） × 每个数占的字节**。一个 70B 参数的模型，每 1000 个 token 的 KV 缓存就要吃几百 MB 显存；上下文拉到 10 万 token，KV 缓存要几十 GB——**比模型本身的权重还大。** 这就是为什么长上下文真正的瓶颈，已经从"算不动"变成了"存不下"：KV 缓存是一个随长度线性增长的显存黑洞。

## 三、上下文窗口：为什么模型"记不住"太长

**上下文窗口（Context Window）**，就是模型一次能"看到"的 token 上限（比如 8K、32K、128K、1M）。超过窗口的输入，模型直接看不见。为什么有限制？两个原因，正好对应两个贵点：

1. **注意力 O(n²)**：窗口翻倍，计算量翻四倍——窗口大到某个点，算不动。
2. **KV 缓存吃内存**：缓存量和 token 数成正比，窗口越大，要存的 KV 越多，显存装不下。

所以"长上下文"一直是各家的军备竞赛：**模型要能看更多，就必须同时解决"算得快"和"存得下"。** 现在的解法有两大家族：

**解法一：稀疏注意力（Sparse Attention）——不每个词都看所有词。** 人的注意力本来就不是平均分配的：读长文时，你主要看附近的字，偶尔跳回前面重要的段落。稀疏注意力把这个直觉数学化，几种形态：

- **局部注意力（滑动窗口）**：每个 token 只看它附近的一小段窗口（比如前后 1000 个 token）。每个 token 只看固定窗口，复杂度从 O(n²) 直接降到 O(n)。
- **全局 token**：在整句话里放几个"特殊 token"，让它们看全部、也让所有 token 看它们——像会议里的"主持人"，谁都能找它。远处的重要信息，通过这个"枢纽"间接传递。
- **组合方案**：Longformer、BigBird 就是把"局部窗口 + 少量全局 token + 随机跳看"组合起来，用接近线性的成本覆盖长距离。

稀疏注意力的代价，是**牺牲了"精确直接关联"**：任意两个词想直接对话，中间要多一层"中转"——信息绕路后会有损失。所以它不是免费的，是拿"质量"换"能跑"。

**解法二：KV 缓存压缩——让"存不下"变小。** 既然瓶颈在显存，就压缩缓存，两条路：

- **量化 KV**：把缓存的数字从高精度压成低精度，体积省好几倍（和第五节量化的思路一样，只是作用在缓存上）。
- **淘汰不重要 token**：有些 token（语气词、重复内容）的 KV 对后面贡献小，直接扔掉——但"谁不重要"要判断，扔错了会丢信息。
- **新一代：MLA（Multi-head Latent Attention，多头潜在注意力）**——DeepSeek 的绝活：不存每个 token 的完整 K/V，而是**存一个"压缩后的公共表示"，需要时再展开**。它把 KV 缓存缩小到原来的几十分之一——这是 DeepSeek 能支持超长上下文、又比同规模模型便宜的关键之一。

对使用者的实用含义：**超长文档别指望模型全记住**——要么用 RAG（检索增强生成，只把相关的几段喂进去），要么让它分段处理。硬塞超长上下文，只会又慢又贵还记不住。

## 四、推理成本：按 token 算钱

你调 API 时，账单是按 **token** 算的（《大模型应用》讲过）。两个数相乘：**单价 × token 数量**。token 数量又分两部分——输入（你发的，含全部历史）+ 输出（模型吐的）。所以：

**成本 =（输入 token 数 + 输出 token 数）× 单价**

这带来几个实用的省钱结论：

- **历史越短越便宜**：每次对话都重发全部历史（回收"模型没记忆"），所以聊天记录越长，输入 token 越多，越贵。**精简历史、主动摘要旧对话**，是省钱第一招。
- **输出比输入贵**（通常单价更高）：让模型"少说废话"（限制 max_tokens、要求简短）能省一大笔。
- **prompt 缓存（Prompt Caching）**：同一段开头（比如系统提示）连续请求时，服务商缓存中间结果，便宜很多——这正是《大模型应用》第六节提过的"提示缓存"，现在你知道它内部是什么了：本质上是 KV 缓存的商业化运用。

## 五、其他提速手段：三个关键工程

### 5.1 量化（Quantization）——把数字压扁

模型的权重默认是高精度浮点数（32 位 FP32，训练常用 16 位 BF16）。但很多时候不需要那么精确——**把"每个数占多少位"压下来，就是量化。** 常见档位：FP16（16 位）→ INT8（8 位整数）→ INT4（4 位）。

为什么省？三处：
- **体积**：INT4 比 FP16 小 4 倍，模型从几十 GB 缩到几 GB。
- **内存带宽**：推理主要卡在"读权重"这一步，权重变小，读得就快（回忆第一节：解码段卡在内存读取）。
- **算力**：整数运算比浮点运算快。

代价是精度损失——但近年研究发现，**只做推理时量化，性能掉得很少**（权重里的信息冗余度比想象的高）。这就是为什么现在几 GB 的模型能跑在普通电脑甚至手机上：**你手机里的"本地小模型"，几乎都是量化后的产物。**

### 5.2 批处理（Batching）——把请求拼起来

GPU 是一台"很多工人并行干活"的机器，你只喂一个请求，大多数工人闲着。**批处理就是同时喂很多个请求，让所有工人满负荷**——摊薄成本，这是 API 服务商降价的底层手段。

但朴素版批处理有个浪费：**必须等整批请求都结束，才能清空让位**——有的请求早回答完了，干等后面慢的。于是有了 **连续批处理（Continuous Batching）**（vLLM 的成名作）：**一个请求回答完，立刻让出位置给新请求，不用等整批。** 像超市收银：不是凑满一队才结账，而是谁先结完谁让位。它把 GPU 利用率拉满，吞吐量大幅提升——今天的高性能推理服务几乎都靠它。

### 5.3 投机采样（Speculative Decoding）——小模型先猜，大模型批改

生成慢的根源：每吐一个词，大模型都要串行跑一次，大部分时间在等"上一个词的结论"。投机采样的思路很鬼：**用一个又快又小的"草稿模型"先一口气猜出后面 k 个词，再让大模型一次性验证这 k 个词对不对（验证可以并行，一次跑完）。**

- 猜对的词直接通过，不重新算——**大模型一次验证，抵过了 k 次生成。**
- 猜错的词，从错的那个开始，大模型自己重新生成。

因为小模型猜得往往挺准（语言有惯性），**平均能提速 2~3 倍。** 类比：**老师（大模型）不逐个听写，而是让学习好的同学（小模型）先写一段，老师只批改——大部分对了，少改错处。** 老师省的是"逐字听写"的时间，学生省的是"重复劳动"。

**总结判断**：推理工程的全部智慧，就一句话——**把"每生成一个词就全量重算"这个笨办法，优化成"能复用就复用、能少算就少算、能并行就并行"。** 对照第一节的两段式推理，每一招各管一段：**KV 缓存**对付解码段的"重复算"（复用中间结果），**稀疏注意力 + KV 压缩**对付长上下文的"存不下"，**量化**对付"读不动"（权重变轻），**批处理**对付"机器闲着"（填满 GPU），**投机采样**对付"串行等"（小模型先跑、大模型批改）。你日常感受到的"大模型还挺快"，背后是这么一整套工程细节在兜底。
